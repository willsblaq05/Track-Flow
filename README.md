# TrackFlow

TrackFlow is a logistics shipment-tracking application for staff and customers.

## Project Status

Phase 1, the backend foundation, is complete. The backend has centralized settings, database-session wiring, CORS, and a versioned health endpoint. Business features are intentionally not implemented yet.

## Product Scope

### Admin/staff

- Authenticate securely with JWT.
- Create and manage shipments, customers, and hubs.
- Control valid shipment status transitions.
- Append shipment events without overwriting history.
- Advance simulated shipment movement.

### Public customer

- Search by tracking number without an account.
- View current status, location, route, delivery estimate, and history.
- View simulated shipment position on a map.

## Architecture Decisions

- Backend: Python, FastAPI, SQLModel, PostgreSQL, and Alembic.
- Frontend: React, Vite, and Tailwind CSS.
- API prefix: `/api/v1`.
- Authentication: JWT access tokens and Argon2 password hashing for staff.
- Events are append-only historical records.
- A shipment stores its current state separately from its events.
- Routes are represented by shipment-specific checkpoints, not hard-coded city logic.
- Movement is manually simulated for the MVP; the backend remains authoritative.
- Public tracking uses dedicated response schemas and does not expose admin data.

## Shipment Statuses

The initial statuses are:

```text
CREATED -> DISPATCHED -> IN_TRANSIT -> ARRIVED_AT_HUB
                                      -> OUT_FOR_DELIVERY -> DELIVERED
```

A shipment may return from `ARRIVED_AT_HUB` to `IN_TRANSIT` when it continues to the next checkpoint. Transition validation belongs in the service layer, not in route handlers.

Every accepted transition must update the current shipment state and append a historical event in one transaction.

## API Groups

The API will use these groups under `/api/v1`:

- `/health`
- `/auth`
- `/shipments`
- `/tracking`
- `/customers`
- `/hubs`

Admin endpoints require authentication. Tracking endpoints are public but return only intentionally public shipment data.

## Local Setup

The backend uses the project virtual environment on Windows:

```powershell
cd Backend
.\venv\Scripts\Activate.ps1
python -m uvicorn main:app --reload
```

The real `.env` file must never be committed. Copy the values from `Backend/.env.example` into a local environment file when configuration is introduced.

The current health check is available at `GET /api/v1/health`.

### Database migrations

Run these commands from `Backend`. Using the virtual environment's Python directly works in both `cmd.exe` and PowerShell:

```text
venv\Scripts\python.exe -m alembic upgrade head
venv\Scripts\python.exe -m alembic current
```

In PowerShell, you can alternatively activate the environment first with `.\venv\Scripts\Activate.ps1` and then use `alembic` directly.

After changing a SQLModel table, create a new migration with:

```powershell
venv\Scripts\python.exe -m alembic revision --autogenerate -m "describe the schema change"
```

Review autogenerated migrations before applying them. The initial schema is in `Backend/alembic/versions`.
